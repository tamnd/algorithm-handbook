A database of houses stores price and floor area, and a buyer asks for every house that costs between two prices and has between two floor areas. Each house is a point in the plane, and the question is a rectangle: report the points inside it, count them, or say whether there are any. Range searching is this problem in general. A set of $n$ points is fixed, many query ranges arrive, and each must be answered much faster than by testing every point. The goal is a query time of the form $O(f(n) + k)$, where $k$ is the number of points reported, with as little space as possible.

How hard the problem is depends on the shape of the range. For axis-parallel boxes, the orthogonal case, the answers are polylogarithmic: a range tree answers a box in the plane in $O(\log^2 n + k)$ time, and $O(\log n + k)$ with fractional cascading, in $O(n \log n)$ space. A kd-tree gets by with linear space but needs $O(\sqrt{n} + k)$ time. For halfplanes, triangles and disks the bounds are polynomial: with linear space, counting the points in a triangle takes about $\sqrt{n}$ time, and lower bounds show that nothing better is possible in the model that covers the known structures. The tools for these ranges are random sampling, cuttings and partition trees, and the VC dimension measures how complex a family of ranges is.

Most entries use one set of eight points, $\{(2,3), (5,4), (9,6), (4,7), (8,1), (7,2), (3,8), (6,6)\}$, and the box $[3,7] \times [2,6]$, which holds $(5,4)$, $(7,2)$ and $(6,6)$. Following this one query through a range tree, a kd-tree, a priority search tree and an offline sweep is the quickest way to compare the methods.
