Some files are too large to sort in main memory. A database that builds an index on a table of a billion rows, a log system that orders a day of events by time, a search engine that inverts its crawl: each must sort data that lives on disk, and memory holds only a small part of it at a time. Here the cost that matters is not the number of comparisons. It is the number of times a block of data moves between the disk and memory, because one disk access takes as long as millions of steps of the processor.

The [external memory model](/external-memory-model/) makes this precise. Memory holds $M$ items, the disk moves blocks of $B$ items, and the cost of an algorithm is the number of block transfers. In this model the plain answer is still a merge sort, but a merge sort of a different shape: it makes long sorted runs in memory, then merges as many runs at a time as memory allows, so that each item crosses the disk boundary only a few times. Nearly every entry of the chapter improves one part of this plan: longer runs, faster merges, more disks, other devices, or no knowledge of $M$ and $B$ at all.

## What the chapter covers

The chapter is in six groups, read in order.

1. **Runs and the merge.** A [sorted run](/sorted-run/) is a piece of the file in order. A [k-way merge](/k-way-merge/) combines $k$ runs with a heap. [External merge sort](/external-merge-sort/) makes runs of $M$ items and merges them $M/B - 1$ at a time, in $O\big(\frac NB \log_{M/B} \frac NB\big)$ block transfers.
2. **Longer runs.** [Replacement selection](/replacement-selection/) makes runs of about $2M$ items on random input, and one run on sorted input. The [run length theorem](/replacement-selection-run-length/) proves the factor of 2.
3. **Keeping the disks busy.** [Double buffering](/double-buffering/) overlaps reading with merging. [Disk striping](/disk-striping/) makes $D$ disks act as one disk with larger blocks, which is simple but not always optimal.
4. **Sorting on tapes.** The [balanced merge sort](/balanced-merge-sort/), the [polyphase merge sort](/polyphase-merge-sort/), the [cascade merge sort](/cascade-merge-sort/) and the [oscillating sort](/oscillating-sort/) arrange runs on a few sequential devices. They are the classic methods of the tape era, and they still teach how to plan passes over data.
5. **Distribution instead of merging.** [External samplesort](/external-samplesort/) splits the file into buckets by sampled splitters and sorts each bucket. [Balance Sort](/balance-sort/) does this on $D$ independent disks and meets the optimal bound for them.
6. **The I/O bound and what meets it.** The [I/O lower bound for sorting](/external-sorting-io-lower-bound/) shows that external merge sort is optimal and extends the bound to $D$ disks. [External permuting](/external-permuting/) asks when it pays to sort keys only and move the records later. [Funnelsort](/funnelsort/) meets the bound in the [cache-oblivious model](/cache-oblivious-model/).

## A first reading

For a first reading, take these eight entries in order: [sorted run](/sorted-run/), [k-way merge](/k-way-merge/), [external merge sort](/external-merge-sort/), [replacement selection](/replacement-selection/), [double buffering](/double-buffering/), [disk striping](/disk-striping/), [balanced merge sort](/balanced-merge-sort/) and [external samplesort](/external-samplesort/). With these you can plan the sort of any file on one disk and count its passes. The tape sorts after the balanced merge, and the entries on several disks, can wait. Read the [I/O lower bound](/external-sorting-io-lower-bound/) once you have met the lower bound for one disk in Volume 1; [funnelsort](/funnelsort/) needs the cache-oblivious model and is best left for last.

From Volume 3 you need the [binary heap](/binary-heap/) and the [priority queue](/priority-queue/), which drive both the k-way merge and replacement selection.
