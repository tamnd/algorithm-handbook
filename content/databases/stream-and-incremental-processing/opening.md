Most queries are asked once, about data that stands still. Some are asked again and again while the data changes: a dashboard that shows sales per region, a warehouse table of daily totals, a rule that flags a suspicious sequence of payments as it happens, a reachability relation over a graph that gains and loses edges. Running such a query from the start after every change wastes almost all of the work, since a small change in the input usually makes a small change in the answer.

This chapter is about computing that change directly. The same idea has two forms. A database keeps a stored query result, a materialized view, and updates it from the changes to the base tables. A stream system runs a standing query over data that arrives without end, keeps only a window or a summary of the past, and emits answers as it goes. The first half of the chapter takes the first form, from delta rules to general models of incremental computation; the second half takes the streams, with their windows, their late data, their joins and patterns, and the engines that run them.

## What the chapter covers

The chapter is in eight groups, read in order.

1. **Stored results.** The [materialized view](/materialized-view/), what it stores and when a query can read it in place of the base tables, and the [view maintenance problem](/view-maintenance/), with the choices between recomputation and deltas and between immediate and deferred maintenance.
2. **Maintaining a view by deltas.** [Incremental view maintenance](/incremental-view-maintenance/) and the [delta rules](/delta-rules/) for each operator of relational algebra, with the counting algorithm for deletions. [Self-maintainable views](/self-maintainable-view/), which need no base table, [deferred maintenance](/deferred-view-maintenance/) from logs, and [higher-order maintenance](/higher-order-ivm/), which stores the deltas of the deltas.
3. **Recursion and general incremental computation.** The [DRed algorithm](/dred-algorithm/) for recursive Datalog views, [DBSP](/dbsp/), which turns a query over streams of changes into an incremental circuit, and [timely](/timely-dataflow/) and [differential dataflow](/differential-dataflow/), which maintain iterative computations by differences indexed by versions and iterations.
4. **Queries over streams.** The [continuous query](/continuous-query/), the [CQL model](/cql-stream-model/) that defines it with windows and relations, the [watermark](/event-time-watermark/) and the [punctuation](/stream-punctuation/) that say when part of the input is complete, and the [dataflow model](/dataflow-model/) of windows, triggers and accumulation.
5. **Window aggregation.** [Panes](/panes-window-aggregation/) for one sliding window, [stream slicing](/stream-slicing/) for many windows at once, and the [FlatFAT](/flatfat/) tree of partial aggregates.
6. **Joining streams.** The [symmetric hash join](/symmetric-hash-join/), which emits each result as soon as both tuples have arrived, and [XJoin](/xjoin/), which keeps working when memory is short and sources stall.
7. **Patterns of events.** [Complex event processing](/complex-event-processing/) and its evaluation by an automaton in [SASE](/sase-event-matching/).
8. **Running a stream engine.** [Chain scheduling](/chain-scheduling/) of operators for small queues, and [asynchronous barrier snapshotting](/asynchronous-barrier-snapshotting/) for consistent checkpoints of a running job.

## A first reading

For a first reading, take these eleven entries in order: the materialized view, the view maintenance problem, incremental view maintenance, delta rules, the continuous query, the CQL model, the watermark, the dataflow model, panes, the symmetric hash join and complex event processing. The first four give the whole idea for nonrecursive views; the rest give the meaning of a stream query, how it copes with late data, and the three basic kinds of stateful operator: the window, the join and the pattern.

The DRed algorithm needs Datalog and semi-naive evaluation and can wait until you have read them. DBSP, timely and differential dataflow, higher-order maintenance, stream slicing, FlatFAT, XJoin, SASE, chain scheduling and barrier snapshotting are advanced or research entries; read them when you need the problem they solve.

## Before you start

You need [relational algebra](/relational-algebra/) from Chapter 40.1, since every delta rule is a rule of the algebra, and for the DRed algorithm and differential dataflow [Datalog](/datalog/) and [semi-naive evaluation](/semi-naive-evaluation/) from the same chapter. Semi-naive evaluation is itself incremental computation: each round joins only the new facts of the round before. The [hash join](/hash-join/) and the [Grace hash join](/grace-hash-join/) of Chapter 40.3 are the batch forms of the stream joins, and [answering queries using views](/answering-queries-using-views/) in Chapter 40.8 shows where a stored view can replace part of a query.

The stream side rests on Volume 19. The [time-based window](/time-based-window/), the [tumbling](/tumbling-window/), [hopping](/hopping-window/) and [session windows](/session-window/), and [sliding window aggregation](/sliding-window-aggregation/) with the [two-stacks queue](/two-stacks-queue/) are the windows that this chapter aggregates. Pane and slice aggregation need a [monoid](/monoid/), and FlatFAT is a [segment tree](/segment-tree/), both from Volume 3. Event patterns are [regular languages](/regular-language/) run by a [nondeterministic finite automaton](/nondeterministic-finite-automaton/), from Volume 9. Timely dataflow orders events by [happened-before](/happened-before/), and barrier snapshotting is a form of the [Chandy-Lamport snapshot](/chandy-lamport-snapshot/), which records a [consistent cut](/consistent-cut/); all three are in Volume 21.
