A table of a million orders fills ten thousand disk pages. A query for one day's orders can read all ten thousand, or it can read the hundred or so that hold that day, if the rows are stored in date order and an index says where the day begins. The difference between the two is the subject of this chapter: how the rows are laid out in pages, which pages are kept in memory, and which auxiliary structures the system keeps, so that each query reads as little as it can.

The cost here is counted in page reads, as in the [external memory model](/external-memory-model/), and the main tool is the [B+ tree](/b-plus-tree/) of Volume 3. The entries are about how a database uses such structures. None of them is free: every index must be updated with the table.

## What the chapter covers

The chapter is in seven groups, read in order.

1. **Pages, files and the buffer pool.** A [slotted page](/slotted-page/) stores records of any length and names each by (page, slot); a [heap file](/heap-file/) is an unordered set of such pages. The [buffer pool](/buffer-pool/) caches pages in a fixed set of frames with pin counts, dirty bits and a replacement policy. The [five-minute rule](/five-minute-rule/) says which pages are worth a frame at given prices, and [DBMIN](/dbmin/) gives each file of a query its own frames, sized by its reference pattern.
2. **Rows, columns and compression.** The [N-ary storage model](/n-ary-storage-model/) keeps whole records together, the [decomposition storage model](/decomposition-storage-model/) keeps each column in its own file, and the [PAX layout](/pax-page-layout/) groups by column inside each page. [Dictionary encoding](/dictionary-encoding/) and [frame-of-reference encoding](/frame-of-reference-encoding/) compress a column so that filters run on the codes, and [late materialization](/late-materialization/) builds the output rows only for the positions that pass.
3. **Access paths and their order.** [Dense and sparse indexes](/dense-and-sparse-index/) differ in how many entries they keep. A [clustered index](/clustered-index/) reads about $h + k/p$ pages for $k$ matches with $p$ rows per page, against about $h + k$ for an unclustered one. A [covering index](/covering-index/) answers a query from its own leaves, and a [partial index](/partial-index/) holds only the rows that satisfy a predicate.
4. **Building and generalizing B+ trees.** [Bulk loading](/bulk-loading-b-tree/) builds a B+ tree from sorted entries and writes each node once. The [prefix B-tree](/prefix-b-tree/) uses the shortest separators, the [GiST](/generalized-search-tree/) is one tree code for B+ trees, R-trees and other indexes, and the [Bw-tree](/bw-tree/) is a B+ tree that never takes a latch.
5. **Indexes for analytic scans.** A [bitmap index](/bitmap-index/) keeps one bit vector per value and answers selections with bitwise operations; [WAH compression](/word-aligned-hybrid-compression/) runs them on compressed bitmaps. A [zone map](/zone-map/) keeps the minimum and maximum of each block, and a [join index](/join-index/) stores the pairs of row ids that join.
6. **Adaptive and learned indexes.** [Database cracking](/database-cracking/) partitions a copy of a column a little more with each range query, and [adaptive merging](/adaptive-merging/) merges a key range out of sorted runs the first time a query asks for it. A [learned index](/learned-index/) predicts the position of a key with a model; the [PGM-index](/pgm-index/) guarantees the error of its prediction, and [ALEX](/alex-learned-index/) accepts inserts.
7. **Choosing indexes.** [Index selection](/index-selection/) picks indexes for a workload under a space budget and is NP-hard. [What-if analysis](/what-if-index-analysis/) costs an index without building it, and the [AutoAdmin](/autoadmin-index-selection/) tool grows a configuration greedily from those costs.

## A first reading

Read the slotted page, the heap file and the buffer pool first: they are the ground floor of every database system. Then read the N-ary and decomposition storage models, dictionary encoding, and dense and sparse indexes. Go on with the clustered index, the covering index, the bitmap index and the zone map, in that order; together they explain most of the plans an optimizer chooses for selections. Finish with index selection, which shows why indexes must be chosen together and not one at a time.

The five-minute rule, PAX, frame-of-reference encoding, the partial index, bulk loading and the join index are short and can follow. DBMIN, late materialization, the prefix B-tree, the GiST, WAH, what-if analysis and AutoAdmin refine ideas you will already know. The Bw-tree, cracking, adaptive merging and the three learned indexes are research topics and can wait until the rest is familiar.

## Before you start

You need the [B+ tree](/b-plus-tree/), the [hash table](/hash-table/) and the [bit vector](/bit-vector/) from Volume 3, and [bitwise operations](/bitwise-operations/) and [bit packing](/bit-packing/) from Volume 2. The buffer pool uses the replacement policies [LRU](/lru/) and [MRU](/mru/) of Volume 26. Bulk loading and adaptive merging start with an [external merge sort](/external-merge-sort/) from Volume 4, and cracking reuses the [partition step](/partition-around-pivot/) of [quicksort](/quicksort/). The learned indexes use [binary search](/binary-search/) and [exponential search](/exponential-search/) from Volume 5 and [least squares](/ordinary-least-squares/) from Volume 25. The GiST generalizes the [R-tree](/r-tree/) of Volume 3, and the Bw-tree rests on the [B-link tree](/blink-tree/) of Volume 3 and on [compare-and-swap](/compare-and-swap/) from Volume 22. WAH is a form of [run-length encoding](/run-length-encoding/) from Volume 24.

Index selection reduces from the [knapsack problem](/knapsack-problem/) of Volume 15 and is [NP-hard](/np-hard/) in the sense of Volume 39; its costs come from the [cost model](/cost-model/) and the [histograms](/histogram/) of the query optimization chapter. The join index assumes the [relational join](/relational-join/) of the query processing chapter.
