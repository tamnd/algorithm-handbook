A type checker reads `fun f -> fun x -> f (f x)` with no annotations and reports the type $(\alpha \to \alpha) \to \alpha \to \alpha$. The parameter `f` is applied to `x` and then to its own result, so its argument type and its result type must be equal, and nothing else is forced. Every other type of the term, such as $(\mathsf{int} \to \mathsf{int}) \to \mathsf{int} \to \mathsf{int}$, is an instance of this one, which is why it is called the principal type. The same checker accepts `let id = fun x -> x in (id 1, id true)` and rejects `fun id -> (id 1, id true)`, although the two programs differ only in where `id` is bound. A name bound by `let` may be used at many types; a parameter may be used at only one. That single rule keeps inference decidable. Lift it, so that parameters may be polymorphic too, and the problem becomes undecidable.

A type system is a set of rules, and the chapter holds three kinds of results about such rules. Some are theorems about one stated calculus: soundness by progress and preservation, strong normalization, principal types. They hold for that calculus, not for a whole language with every feature added. Some are algorithms with bounds: checking the simply typed lambda calculus in linear time, inferring ML types by unification, solving refinement constraints with a bounded number of solver queries. The rest are limits: ML typability is DEXPTIME-complete, and inference with polymorphic recursion or for System F is undecidable. Each entry says which kind it gives.

Some neighbouring topics have their own entries elsewhere. Unification, most general unifiers and semi-unification are in Volume 16, together with the SMT solvers that refinement types call. Beta reduction and the Church-Rosser theorem are in Volume 9. Borrow checking runs on the control flow graph of Chapter 34.2 and uses the liveness analysis of Chapter 34.3. This chapter links to those entries and does not repeat them.

3. **Where inference stops.** [DEXPTIME-completeness of ML typability](/ml-typability-dexptime-completeness/), the [undecidability of polymorphic recursion](/polymorphic-recursion-undecidability/), [System F](/system-f/), the [undecidability of System F inference](/system-f-inference-undecidability/) and [bidirectional type checking](/bidirectional-type-checking/).

## A first reading

Take these twelve entries in order: the type system, the simply typed lambda calculus and type soundness; the type inference problem, let-polymorphism, the Hindley-Milner type system, algorithm W and the principal type theorem; the value restriction; System F; bidirectional type checking; and subtyping. They give the rules, the soundness proof, the inference algorithm that ML compilers run with its guarantee, and the two ways out when inference is not enough: write more annotations, or let one type stand for another.

Algorithm J and the constraint-based form can wait until you need an implementation. The three limit theorems of the third group are proofs by reduction, best read after the algorithms. Type classes and their two compilation schemes stand on their own once Hindley-Milner is clear. Of the last two groups, read linear types before borrow checking and refinement types before liquid types; the other entries can be taken in any order.
