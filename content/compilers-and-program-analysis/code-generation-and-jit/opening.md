Take this loop in three-address code: `d = n; L1: a = d + 1; b = a + d; c = a + 1; d = b - c; d = d % c; br d L1 L2; L2: ret d`. At no point are more than two of its names live, so two registers should be enough, and they are. But the [interference graph](/interference-graph/) of the loop is the cycle $a, b, c, d$ of length four, every vertex has degree 2, and [Chaitin's allocator](/chaitin-register-allocation/) with $k = 2$ finds no vertex of degree below 2 and spills one. [Briggs's optimistic coloring](/briggs-optimistic-coloring/) colors the same graph with two colors. Put the loop in strict SSA form and the cycle falls apart into a path, because the [interference graphs of strict SSA programs are chordal](/ssa-chordal-interference-theorem/) and need exactly as many colors as the largest number of names live at once.

This chapter is about the last steps of a compiler, which turn an intermediate representation into machine code, and about compilers that do this while the program runs. Code generation splits into three problems: [instruction selection](/instruction-selection-problem/) chooses the instructions, [register allocation](/register-allocation-problem/) maps values to registers and memory, and [instruction scheduling](/instruction-scheduling-problem/) orders the instructions for the pipeline. Each is NP-hard in its general form, and each has cases with exact polynomial answers. Covering a tree with tiles by dynamic programming is optimal for the cost model of the tiles, while covering a DAG is NP-complete. Coloring an interference graph with $k \ge 3$ registers is NP-complete, coloring the chordal graph of a strict SSA program is easy, and choosing what to spill or which copies to remove stays NP-hard even then. Scheduling a block is NP-complete even on a machine that issues one instruction per cycle, once latencies are part of the input. Most methods that compilers use are heuristics: maximal munch, Chaitin's and Briggs's simplify rules, conservative coalescing, linear scan, list scheduling and iterative modulo scheduling. Each entry says what it proves, and the rest is measured.

The second half is about just-in-time compilers. They interpret first, count, compile the hot parts, and guess from what they have seen: the receiver classes at a call site, the types of values, the path through a loop. Each guess is a guard in the compiled code, and deoptimization brings the run back to the interpreter when a guard fails. If the compiler keeps one invariant, that the rebuilt frames are a state the interpreter passes through, the run ends exactly as a plain interpreted run would; that part is proved. Speedups from a JIT compiler, from inlining or from a better tier are measurements on named programs and machines, never guarantees.

Neighbouring chapters hold the analyses this chapter uses: [liveness](/live-variable-analysis/) in Chapter 34.3, [SSA form](/static-single-assignment-form/) and the [conversion out of SSA](/out-of-ssa-translation/) in Chapter 34.2, and [function inlining](/function-inlining/) and [profile-guided optimization](/profile-guided-optimization/) in Chapter 34.4.

## A first reading

Take these thirteen entries in order: the activation record and just-in-time compilation; the instruction selection problem, Sethi-Ullman numbering and Aho-Johnson code generation; the register allocation problem, the interference graph, Chaitin's allocator and Briggs's optimistic coloring; linear scan and the SSA chordal interference theorem; the instruction scheduling problem; and deoptimization. They give the three problems of the back end with their exact cases and their main heuristics, and the one contract that every speculative JIT compiler keeps.

Threaded code, maximal munch, BURS, the hardness proofs, the spill and coalescing group, local and SSA-based allocation, the regional and loop schedulers, the dispatch caches and the last group can wait for a second pass.
